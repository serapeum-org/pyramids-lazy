    Backend contract#

    The object pyramids-core resolves and dispatches to. One instance exposing one method per lazy operation, two class accessors (lazy_netcdf_type and lazy_feature_collection_type, which hand core the classes it forwards its own public names to) and an api_version core checks before using it.
    Entry-point group pyramids.compute_backend
    Entry point lazy = pyramids_lazy.backend:backend
    Fallback pyramids_lazy.get_compute_backend()
    Contract version API_VERSION = 2
    Authoritative Protocol pyramids.base._compute_backend.ComputeBackend

    Every method is a thin forwarder that imports its implementation module inside the method body, so an operation's own module (_zarr, _kerchunk_facade, _vector_read, …) is loaded only when that operation is first used.

    That is a statement about the per-operation modules, not about dask. With the [parquet] extra installed, importing pyramids_lazy pulls in dask (core, array and dataframe) along with dask_geopandas, pyarrow, pandas, geopandas and scipy — though not distributed, zarr or xarray, which stay out until an operation needs them. None of this is caused by anything in this package. Nothing in pyramids_lazy, and nothing in pyramids-core, imports dask at module scope. The chain is:

    1. pyramids_lazy/__init__.py re-exports LazyNetCDF eagerly, which imports pyramids.lazy_support;
    2. that facade imports core subpackages, reaching pyramids.feature.__init__;
    3. which probes for dask_geopandas at module scope — a try/except OptionalPackageDoesNotExist that sets the _HAS_DASK_GEOPANDAS flag core uses for dispatch;
    4. and dask_geopandas imports dask.

    So the cost appears only when the optional dependency is present. Blocking dask_geopandas to simulate a bare install, the probe fails, the flag goes False and no dask is imported:

    Imported Modules dask present
    pyramids 306 no
    pyramids.feature, with dask_geopandas blocked 855 no
    pyramids.feature 1397 yes
    pyramids.dataset 1690 yes
    pyramids_lazy 1868 yes

    Measured:

    Measured in two separate interpreters:

    $ python -c "import sys, pyramids;      print(len(sys.modules), 'dask' in sys.modules)"
306 False
$ python -c "import sys, pyramids_lazy; print(len(sys.modules), 'dask' in sys.modules)"
1868 True

    What the deferred imports buy is therefore narrower than "no dask on import": zarr stays out until a Zarr operation runs, and the per-operation modules stay unloaded until used.

    Why a singleton#

    The Protocol describes a single object rather than a class discovered per source, mirroring core's plot-backend seam rather than its raster/vector driver seam. Both discovery paths resolve to the same module-level backend instance.

    That is a statement about which object they return, not about patching. Core caches the backend it resolved, so a test that replaces pyramids_lazy.backend after resolution will not be seen by core until the cache is cleared (clear_compute_backend_cache).

    class LazyComputeBackend:
    """Concrete ``pyramids.compute_backend`` backend for the dask/zarr lazy layer.

    See ``pyramids.base._compute_backend.ComputeBackend`` for the authoritative method contract and
    signatures; every Protocol method is implemented here one-for-one. ``classify_zarr_store`` is an
    additional, duck-typed extension core reaches via ``getattr`` -- deliberately not a Protocol
    member, so a backend predating it is not rejected by core's structural check.
    """

    api_version: int = API_VERSION

    def lazy_netcdf_type(self) -> type:
        """Return the class :meth:`build_lazy_cube` produces.

        Core forwards its public ``pyramids.netcdf.LazyNetCDF`` name (and the ``isinstance`` checks
        that go with it) to this, instead of importing ``pyramids_lazy`` itself, so the entry-point
        seam stays honest about which backend is installed.
        """
        from pyramids_lazy._lazy_cube import LazyNetCDF

        return LazyNetCDF

    def lazy_feature_collection_type(self) -> type:
        """Return the class the lazy vector reads produce.

        Backs core's public ``pyramids.feature.LazyFeatureCollection`` and ``is_lazy_fc``.

        A method, NOT a property: ``runtime_checkable`` isinstance evaluates data members with
        ``getattr``, so as a property this body ran whenever core merely type-checked the backend.
        Importing the module needs ``dask-geopandas`` (the ``[parquet]`` extra), so that made the
        whole backend fail its structural check in every env without that extra -- and core, which
        treats a failing backend as one to skip, then fell back to eager execution for raster and
        cube work that never needed vectors at all. As a method the import is deferred to the call,
        where the branded hint is the right answer.
        """
        from pyramids_lazy._lazy_collection import LazyFeatureCollection

        return LazyFeatureCollection

    def read_array_lazy(
        self, dataset: Any, *, chunks: Any, lock: Any = None, **kwargs: Any
    ) -> Any:
        """Lazy dask-backed read of a raster/variable (``Dataset``/``NetCDF`` ``read_array``).

        ``dataset`` is accepted for the Protocol; the object-specific prep (path, variable name,
        spatial-dim orientation, manager hook, cloud env) is done by core and forwarded in
        ``kwargs`` to :func:`build_lazy_array`.
        """
        from pyramids_lazy._lazy import build_lazy_array

        return build_lazy_array(chunks=chunks, lock=lock, **kwargs)

    def build_lazy_cube(self, netcdf: Any, chunks: Any) -> Any:
        """Build the lazy cube view for ``NetCDF.chunk`` (returns a ``LazyNetCDF``)."""
        from pyramids_lazy._lazy_cube import build_lazy_cube

        return build_lazy_cube(netcdf, chunks)

    def to_dask_dataframe(
        self, netcdf: Any, *, variables: Any, dropna: bool, chunks: Any
    ) -> Any:
        """Back ``NetCDF.to_dask_dataframe``."""
        from pyramids_lazy._to_dask_dataframe import to_dask_dataframe

        return to_dask_dataframe(
            netcdf, variables=variables, dropna=dropna, chunks=chunks
        )

    def to_kerchunk(self, source: Any, output_path: Any, **kwargs: Any) -> dict:
        """Back ``NetCDF.to_kerchunk`` (single-file kerchunk manifest)."""
        from pyramids_lazy._kerchunk_facade import to_kerchunk

        return to_kerchunk(source, output_path, **kwargs)

    def combine_kerchunk(self, paths: Any, output_path: Any, **kwargs: Any) -> dict:
        """Back ``NetCDF.combine_kerchunk`` / ``DatasetCollection.to_kerchunk``."""
        from pyramids_lazy._kerchunk_facade import combine_kerchunk

        return combine_kerchunk(paths, output_path, **kwargs)

    def open_mfdataset(self, paths: Any, variable: Any, **kwargs: Any) -> Any:
        """Back ``NetCDF.open_mfdataset`` (dask-stacked multi-file read)."""
        from pyramids_lazy._mfdataset import open_mfdataset

        return open_mfdataset(paths, variable, **kwargs)

    def open_mesh_mfdataset(self, paths: Any, **kwargs: Any) -> Any:
        """Back ``MeshDataset.open_mfdataset(chunks=...)`` (dask-stacked multi-file mesh read).

        An **additive, duck-typed** extension core reaches via ``getattr``, like
        :meth:`classify_zarr_store` and deliberately **not** a ``ComputeBackend`` Protocol member:
        the Protocol is ``runtime_checkable`` and core drops any backend failing its structural
        ``isinstance`` check, so adding a method there would reject every already-released plugin.
        Returns a :class:`~pyramids_lazy._mesh_mfdataset.LazyMeshDataset`; see
        serapeum-org/pyramids-core#1458.
        """
        from pyramids_lazy._mesh_mfdataset import open_mesh_mfdataset

        return open_mesh_mfdataset(paths, **kwargs)

    def lazy_mesh_type(self) -> type:
        """Return the class :meth:`open_mesh_mfdataset` produces (the lazy time-stacked mesh).

        The mesh analogue of :meth:`lazy_netcdf_type`, provided so core *can* forward a public
        ``pyramids.netcdf.ugrid.LazyMeshDataset`` name (and its ``isinstance`` checks) to this
        without importing ``pyramids_lazy`` itself. **No released core consumes it yet** -- unlike
        ``lazy_netcdf_type`` / ``lazy_feature_collection_type``, which core does forward: core's
        ``MeshDataset.open_mfdataset(chunks=...)`` reaches ``LazyMeshDataset`` only as the return of
        :meth:`open_mesh_mfdataset` and never asks for its type. This accessor is therefore dead
        until someone wires that forwarding; it is kept for parity and that future use. An additive,
        duck-typed accessor core would reach via ``getattr`` -- see :meth:`open_mesh_mfdataset`.
        """
        from pyramids_lazy._mesh_mfdataset import LazyMeshDataset

        return LazyMeshDataset

    def write_dataset_to_zarr(self, dataset: Any, store: Any, **kwargs: Any) -> Any:
        """Back ``Dataset.to_zarr``."""
        from pyramids_lazy._zarr import write_dataset_to_zarr

        return write_dataset_to_zarr(dataset, store, **kwargs)

    def read_dataset_from_zarr(self, store: Any, **kwargs: Any) -> Any:
        """Back ``Dataset.from_zarr`` (returns a ``Dataset``)."""
        from pyramids_lazy._zarr import read_dataset_from_zarr

        return read_dataset_from_zarr(store, **kwargs)

    def classify_zarr_store(
        self, store: Any, storage_options: dict[str, Any] | None = None
    ) -> str:
        """Back core's ``Dataset.read_file`` Zarr routing: classify a ``.zarr`` store.

        Returns ``"single"`` / ``"cube"`` / ``"other"``. Core applies the cheap suffix gate itself
        and asks the backend to look inside a ``.zarr``; opening the store needs the optional
        ``zarr`` package, which lives here, so the classification does too. An unreadable or foreign
        store is reported as ``"other"`` (never raises) so core falls back to GDAL.
        """
        from pyramids_lazy._zarr import classify_zarr_store

        return classify_zarr_store(store, storage_options)

    def write_collection_to_zarr(
        self, collection: Any, store: Any, **kwargs: Any
    ) -> Any:
        """Back ``DatasetCollection.to_zarr``."""
        from pyramids_lazy._collection_zarr import write_collection_to_zarr

        return write_collection_to_zarr(collection, store, **kwargs)

    def read_collection_from_zarr(
        self, collection_cls: Any, store: Any, **kwargs: Any
    ) -> Any:
        """Back ``DatasetCollection.from_zarr`` (returns a ``DatasetCollection``)."""
        from pyramids_lazy._collection_zarr import read_collection_from_zarr

        return read_collection_from_zarr(collection_cls, store, **kwargs)

    def read_vector_lazy(self, source: Any, **kwargs: Any) -> Any:
        """Back ``FeatureCollection.read_file(backend="dask")``."""
        from pyramids_lazy._vector_read import read_file_dask

        return read_file_dask(source, **kwargs)

    def read_vector_parquet_lazy(self, source: Any, **kwargs: Any) -> Any:
        """Back ``FeatureCollection.read_parquet(backend="dask")``."""
        from pyramids_lazy._vector_read import read_parquet_dask

        return read_parquet_dask(source, **kwargs)

    Optional-extra handling#

    pyramids_lazy._optional #

    Branded guards for this backend's own optional dependencies.

    Core's extra_hint composes hints for core's extras, so it names pyramids-core[parquet]. The lazy-vector path ships in THIS distribution's [parquet] extra, so its hints have to name pyramids-lazy[parquet] instead. The guards live in their own module so a module-scope import can be branded without _vector_read and _lazy_collection importing each other.

    LazyExtraNotInstalled #

    Bases: ModuleNotFoundError

    A dependency from one of this backend's optional extras is missing.

    Subclasses :class:ModuleNotFoundError, not just :class:ImportError, deliberately. Tooling treats the two differently: :func:pytest.importorskip skips on ModuleNotFoundError and re-raises every other ImportError so a real breakage is never swallowed, and plenty of library code guards optional imports with except ModuleNotFoundError. Raising a plain ImportError here therefore turned "this extra is not installed" into a hard error for every such caller -- it aborted collection across pyramids-core's whole matrix once. Being a ModuleNotFoundError keeps those callers working while the message stays branded.
